# DEEPoS на R36S‑V20. Сохранения, совместимость и план передачи разработки

Этот документ фиксирует состояние после проверки 0.50 и установки 0.51. Он дополняет [FIRMWARE-SPEC.md](FIRMWARE-SPEC.md), [правила репозитория](../AGENTS.md), [аудит всех 16 настроек](V20-ARCHITECTURE-AUDIT.md) и [метрики](metrics.md). Для следующего агента подготовлены [спецификация настроек и архитектуры](V20-SETTINGS-ARCHITECTURE-SPEC.md) и [стартовый промпт](V20-AGENT-START.md).

## Точка входа для следующего агента

1. Работай из Git-репозитория `deepos`. Сними `git status --short --branch`, `git log -5 --oneline` и `git diff`. Ветка исправлений 0.51 называется `fix/v20-game-exit`. Не сбрасывай чужие изменения. Прочитай `AGENTS.md` и §1, §8, §9, §13, §17 основной спецификации. Сверь версию в Git и на устройстве отдельно.
2. Начни с инвентаря и матрицы P0. Реализуй общий игровой сеанс P1 и сохранения P2, затем пройди P3–P6 по всей матрице. Промежуточный тест открывает следующий этап. Для завершения этапа нужны результаты по всем его строкам. Обновляй журнал и метрики, используй отдельную ветку для следующего блока. Публикация, перезапись SD и перезагрузка физической консоли требуют действующего разрешения пользователя.
3. Перед записью проверь `cat /etc/deepos-version`, `cat /proc/cmdline`, метки разделов в `/sys/class/block/*/uevent` и текущую запись extlinux. В известной конфигурации работали из B, A резервный. Номера устройств сверяй заново. BOOT, ядро, DTB, A, DATA и ROMS не входят в обновление B. Для записи пользовательских разделов нужны резервная копия и подтверждение согласно `AGENTS.md`.
4. Если доступна консоль по USB, сначала делай только чтение. Windows с AmneziaVPN терял DHCP даже при разрешении адреса консоли. Для обслуживания с включённым VPN существует локальный мост через ВМ `DEEPoS USB recovery`, подключённую к USB NCM. Это обход на данном ПК. Требование работы по кабелю без ВМ с активным VPN остаётся отдельной задачей. Не отключай VPN или его общие правила. Отладочный сетевой доступ зависит от `DEBUG.ON` и предназначен для доверенного локального подключения.
5. Воспроизводи симптом через обычное меню. Сохрани версии рантайма, ядра и образа, эффективную конфигурацию и короткий журнал. Разделяй результаты стенда ARM64, теста ввода и физического прогона. Сначала установи, где прервалась цепочка, затем меняй минимальный компонент.

### Как вести и закрывать матрицу

Одна строка на проверяемое сочетание системы, рантайма, ядра и его версии, формата, способа запуска и источника содержимого. Для портов подставлять ID и версию порта. Связывать строку с отдельным именованным тестовым случаем и журналом. Рекомендуемые столбцы для отчёта:

```text
firmware board environment system runtime core build content_id format source bios
start video audio controls sticks volume exit sram state reboot recovery performance evidence
```

Для каждой проверки использовать `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN` или `NOT_APPLICABLE`. `BLOCKED` содержит конкретный BIOS, требуемые данные, рантайм или следующую проверку. `NOT_APPLICABLE` требует подтверждения, что возможность отсутствует по назначению, например у игры без сохранения. Замены ядер и результаты на стенде ARM64 связывать с соответствующей строкой. Статус аппаратной проверки выставлять на V20. Новые или изменённые строки сразу попадают в список повторного прогона. После правки общего слоя повторять автоматическую проверку всей матрицы и аппаратные тесты всех семейств, затронутых изменением. Для полной приёмки у каждой обязательной строки должны быть доказательства по всем применимым полям. Разрешённые исключения публикуются с причиной и точным объёмом поддержки.

### Требования к сохранениям и состояниям

- **Разные типы.** Внутриигровые файлы (`.srm`, `.sav`, EEPROM, карты памяти, конфигурации порта) и снимки памяти эмулятора хранятся отдельно. Обычный запуск использует подходящий внутриигровой сейв. Состояния доступны отдельной операцией с выбором слота. Для новых данных использовать DATA ext4. Сохранить чтение текущих путей ROMS и форматов из K4. Расхождение фактических путей `saved` и §8 основной спецификации закрыть совместимостью при чтении и отдельным документированным решением о миграции.
- **Идентичность.** В метаданных состояния хранить версию схемы, идентификатор системы и содержимого, диск и комплект для многодисковых игр, идентификатор рантайма, идентификатор и сборку ядра, номер слота, длину, контрольную сумму и отметку времени. Учитывать параметры, влияющие на сериализацию. Имя файла отображается пользователю и помогает найти старую копию. Совпадение имени или заголовка недостаточно для автоматического переноса. Ссылаться на алгоритм ROM ID из §8 и хранить его версию. При совпадении быстрого ключа двух образов уточнять идентичность хешем данных. Полное хеширование можно делать по запросу или при первом сохранении с кэшем. Запуск большой игры не зависит от полной хеш-проверки библиотеки.
- **Смена ядра.** При смене сборки или ядра предлагать новый запуск с совместимым внутриигровым сейвом либо прежнее ядро для существующего состояния. Автозагрузка разрешена только с проверенной совместимостью. Версия по умолчанию совпадает с записанной. Держать старые состояния отдельно от новых. Копировать SRAM между ядрами только после подтверждения общего формата или явного выбора пользователя. Не конвертировать по расширению. Бэкап сохраняется и при откате прошивки A/B.
- **Целостность.** Данные и метаданные записывать в новые файлы на одном ext4, завершить запись `fsync`, опубликовать одной операцией обновления ссылки на поколение и синхронизировать каталог. До публикации прежнее поколение читается. Безопасное восстановление разбирает только собственные временные файлы и оставляет последнюю целую версию. Проверять доступное место, контрольную сумму и границы размера. Для конкурирующих операций применять блокировку на игру либо короткую сериализацию без нового демона.
- **Legacy и импорт.** Сначала инвентаризировать фактические каталоги в режиме чтения. Показывать источник, конфликт версий и объём. Копировать в staging, проверять формат и хеш, публиковать после проверки. Если соответствие названия неоднозначно, показать список и сохранить исходные файлы. Не переименовывать и не стирать пользовательские файлы автоматически. Импорт архива допускает только утверждённую структуру обычных файлов, проверяет пути, объём и количество записей; ссылки и выход из staging отклоняются.
- **Резервное копирование.** Включить всё управляемое DEEPoS, отдельно известные каталоги портов и legacy RetroArch. Создавать согласованный снимок в покое или после завершения записи рантаймом. Архив хранит версионированный манифест с хешами. Проверять чтением до ротации. Дать экспорт на другой носитель и импорт с предварительным просмотром. Копия на той же карте нужна для ошибок пользователя. Защита от отказа карты требует копии на другом носителе.
- **Выход и питание.** Сначала дать рантайму штатно сохраниться. По завершении проверить запись и только тогда показывать «Состояние сохранено». На коротком отключении питания допустима потеря ещё не зафиксированного прогресса; предыдущий подтверждённый файл должен читаться. При поломке состояния показать причину и позволить обычный запуск. Выход `Select + Start` доступен всегда, даже при отсутствующей поддержке стейтов.
- **Интерфейс.** «Продолжить с состояния» показывается при подтверждённом совместимом снимке. «Запустить игру» использует игровой сейв по правилам рантайма. «Состояния» показывает слот, время, ядро и совместимость. Пять управляемых слотов и до десяти архивов из §8 применяются только к управляемому набору. Сторонние или ручные файлы не попадают под ротацию. Для порта без стейтов показывать доступные функции сохранения.

- [ ] Сопоставить доступные пользователю ROM и порты с матрицей. Для каждой строки назначить совместимый образец и точку проверки в игре либо указать конкретную недостающую зависимость. Для общих форматов выбрать дополнительные случаи с Unicode, архивом, относительной ссылкой и несколькими дисками. Сохранить исходный отчёт до первого изменения.

### P1. Единый жизненный цикл игры и диагностический результат

- [ ] Разметить точки входа в `apps/launcher/src/main.c`, `board/r36s-v20/data/emulators.toml`, `retroarch-game.sh`, `run-port.sh`, `perf-boost.sh`. Ввести единый результат запуска с системой, относительным путём ROM, источником TF1/TF2, выбранным рантаймом и ядром, кодом завершения, сигналом и подтверждённым статусом сохранения. Ограничить размер лога, долговременную запись делать только по запросу или при ошибке.
- [ ] Формировать уникальную конфигурацию в `/run` на игру. Сохранять доказанный порядок «база → пользователь → системные хоткеи → текущая игра». Обрабатывать реальные формы `--appendconfig` и `#include`. Перед изменением профиля получить действующие governor и пределы CPU/GPU. Восстановить именно их. Снабдить существующий watchdog идентификатором сеанса либо заменить его коротким общим механизмом очистки. Завершившийся сеанс не меняет governor нового.
- [ ] В `tests/launch_test.py` проверить обычный выход, ненулевой код, TERM, зависший потомок, двойной запуск, завершение прошлого сеанса во время следующего и отсутствие эмулятора. На V20 проверить процесс, каталог `/run`, GPU/CPU до, во время и после. Должна остаться только активность сеанса, который сейчас запущен. Нативное завершение должно успевать записать SRAM. Замерить задержку перед тем как менять текущие 250 мс ожидания и 1,5 с после TERM.

### P2. Сейвы, восстановление и «Продолжить»

- [ ] Начать с чтения инвентаря и резервной копии. Проверить legacy по нескольким ядрам и одному порту, сохранив контрольные суммы до/после. Доработать `apps/saved/src/saved.c` и `tests/saved_test.py`, чтобы потеря питания после каждого барьера, нехватка места, повреждённые метаданные и повтор операции сохраняли читаемое старое поколение. Проверить также одновременную запись одного слота двумя вызовами.
- [ ] Реализовать общий контракт для RetroArch, самостоятельных эмуляторов и портов. Каждый адаптер объявляет виды сохранений, получает стабильный ключ и каталог, определяет фактически созданный файл и сообщает результат. Для RetroArch использовать `retroarch-game.sh`, маршрутизацию держать в общем игровом сеансе. Проверить точный синтаксис загрузки состояния на импортированной сборке. Параметр `savestate_auto_load` связан с автофайлом рантайма. Результат обычного `state_slot` подтверждать фактической загрузкой.
- [ ] Закрыть проверки сохранений для каждого применимого маршрута матрицы. Минимальный цикл включает прогресс, штатный выход, повторный запуск, перезагрузку платы и чтение прогресса. Для стейта зафиксировать положение или счёт, восстановить в том же ядре, проверить блокировку несовместимой сборки и восстановление после возврата к прежней. Для многодисковых игр сохранить идентичность комплекта и диска. Повторить на TF2 только для чтения в тех маршрутах, которые его поддерживают. Выключение питания проверять на тестовой SD с тестовыми файлами после согласования.
- [ ] Доработать `modules/saves/root/saves-backup.sh` и покрывающие его тесты. Проверить архив при неполной записи, конфликте, нехватке места, одинаковых отметках времени, восстановлении на пустой тестовый каталог и попытке выхода из каталога через архив. Импорт требует осознанного выбора при конфликте. Адаптеры PPSSPP, Flycast и портов добавлять только после нативной проверки формата.

### P3. Матрица совместимости, BIOS и запуск ROM

- [ ] Сверить все системы из §9 `FIRMWARE-SPEC.md` с `board/r36s-v20/data/emulators.toml`, реестром `cores.tsv`, фактически установленными библиотеками и `board/r36s-v20/data/bios-required.tsv`. У каждого ряда должны быть поддерживаемые расширения, зависимость от BIOS, команда запуска, применимые профили и причина отсутствия проверки. Статусы `ядро загружается`, `ROM стартует`, `управление`, `звук`, `сейв`, `стейт`, `выход`, `производительность` ведутся независимо. Для игр без стейта отмечать штатное ограничение.
- [ ] Добавить повторяемый локальный инструмент аудита под `tools/` и проверить его на маленьких открытых ROM или образцах пользователя. Не включать игру, BIOS или пользовательскую библиотеку в репозиторий. Записывать версии, источник TF1/TF2, окружение ARM64 или V20, длительность и короткие причины отказа. Не считать ядро прошедшим при загрузке ELF, если контент не проверен.
- [ ] Покрыть расширения, регистр, Unicode, пробелы, одинаковые названия на TF1 и TF2, ZIP, CHD, CUE/BIN, M3U и диск с относительными ссылками. Архив обрабатывает совместимый эмулятор или утверждённый ограниченный распаковщик. Разрешение связанных файлов не выходит за каталог библиотеки. Неполный комплект должен давать понятную причину. Дополнительно проверить полноценный образ Dreamcast, штатный файл ScummVM, EGL на N64 и нативный PPSSPP.
- [ ] Расширить `bios-check.sh` и раздел «Эмуляторы» в лаунчере. Показать обязательный файл, альтернативу, HLE, несовпадение контрольной суммы и фактически используемый каталог. Загрузка выполняется локально. Показать отсутствующий рантайм или зависимость до чёрного экрана. Пункты диагностики и настройки допускают экспорт текстового отчёта без частных путей и адресов.

### P4. Проверка портов и производительности

- [ ] Проверять каждый включённый или установленный порт по метаданным устройства и рантайма. Отличать установленную игру, порт без данных и служебный пункт. Для каждого порта проверить обычный экран запуска, выход и собственные сейвы. Для каждого семейства рантаймов проверить запуск после обновления, отсутствие требуемой библиотеки и повреждённые данные. Список форматов и зависимостей брать из официальных метаданных PortMaster.
- [ ] Записать короткий замер кадров и аудио для каждой игровой строки V20. Провести длинные прогоны на каждом сочетании видеобэкенда, аудиовывода и класса нагрузки, а также на каждом маршруте с пропусками, фризами или перегревом в коротком тесте. Сравнивать несколько прогонов на том же ядре, содержимом и участке игры. Записывать время кадров и p95/p99, `EPIPE` либо счётчик underrun, температуру, governor CPU/GPU, PSI и RSS, восстановление после выхода. Проверять динамик, наушники, боковые кнопки и отсутствие двойного шага громкости. Целевые пределы брать из §1 и §11 основной спецификации.
- [ ] Менять латентность, потоковый вывод или governor точечно при воспроизводимом улучшении. На V20 `video_threaded` ранее ломал KMS. Параметр `SDL_AUDIO_SAMPLES` работает для SDL2, если приложение само не задало размер. Опцию SDL3 не использовать как доказательство изменения буфера. Проверять фактический ALSA `hw_params`. Ограничить частоту рисования лаунчера фокусом и событиями пользователя.

### P5. Настройки, управление и темы

- [ ] Использовать [таблицу всех 16 настроек](V20-ARCHITECTURE-AUDIT.md). Сгруппировать их по разделам «Управление», «Экран и звук», «Игры», «Система», «Диагностика». Частые действия сохраняют короткий путь. Для яркости, громкости, профиля питания и USB показывать фактическое состояние. Для игровых настроек показывать, к какому рантайму они применяются, источник значения и действие сброса.
- [ ] Для кнопок и обоих стиков проверить на физическом устройстве крайние положения, центр, дрейф, диагонали и быстрое повторное нажатие. В настройках разрешать калибровку с отменой и возвратом к известной схеме. Эмулятор сохраняет сырые оси и собственную раскладку, пока пользователь не изменил профиль игры. `Select + Start` проверять в диагностике и в каждой игровой строке матрицы. Громкость и отображение проверять в каждом используемом видеорежиме и семействе аудиовывода.
- [ ] Сохранить 12 встроенных тем и аварийную базовую тему. Пользовательские темы остаются данными с ограничением размеров. Проверить навигацию и читаемость каждой компоновки на 640×480, память в простое и p95 перерисовки. [Формат тем](THEMES.md)

- [ ] Проверить отдельные режимы USB-сети и USB-файлов. USB-файлы должны передавать владение ROMS одному участнику и восстанавливаться после корректного извлечения. Для диагностики исследовать статический локальный адрес и USB ACM как запасной ход. На ПК проверить реально работающий канал с VPN и без VPN, DHCP, обычное переподключение, холодную загрузку и неизменность режима по умолчанию. - [ ] Для тестового обновления подготовить предыдущий проверенный образ и сверить SHA‑256 обоих файлов. Считать обратно известное число байт до отката/после записи и проверять каждую контрольную сумму. После загрузки сверить версию, `PARTLABEL`, `checks.txt`, рабочую панель, ввод, звук, быстрый выход, повторный запуск. Не подменять эту проверку `--selftest` в контейнере.

## Команды для стенда

Собирать и запускать в отдельном каталоге внутри контейнера. Рабочая копия Windows может содержать AArch64-объекты, а `tests/run-all.sh` ожидает `/w`. Для полного прогона использовался образ `deepos-build:local` с `mkimage`. Базовый `deepos-cross:local` подходит для сборки rootfs, но в нём отсутствовал `mkimage` для одного из BOOT-тестов.

```sh
git status --short --branch
git diff --check
# В deepos-build:local, из изолированной копии в /w
export CFLAGS='-O2 -std=c11 -Wall -Wextra -Werror -Wno-format-truncation -pedantic -D_GNU_SOURCE'
sh tests/run-all.sh
python3 tests/saved_test.py
python3 tests/launch_test.py
python3 tests/board_test.py
```

После изменений версии обновить только ожидаемые строки `tests/golden/hashes.json` через `python3 tests/run.py --update`. Перепроверить staged diff командой `tools/check-secrets.ps1 -Staged`. Изменения сохранений, BOOT или аппаратных дефолтов сопровождаются выводом конкретных тестов и замером по образцу [metrics.md](metrics.md).

Для сборки прошивки монтировать исходники в `/src` только для чтения и локальный `build/` в `/w/build` в контейнере `deepos-cross:local`. Команды ниже используют пакеты, с которыми собрана 0.51. При отсутствии пакета сначала восстановить его по [EMULATORS.md](EMULATORS.md) и сверить состав. Записать контрольные суммы входов и итоговую версию в журнал. Для отдельного кандидата использовать собственные `STAGE` и `OUT`.

```sh
cd /w
tar -C /src --exclude=.git --exclude=build --exclude=tests/out --exclude='*.o' -cf /tmp/deepos-src.tar .
tar -C /w -xf /tmp/deepos-src.tar
export PORTMASTER_PACKAGE=/w/build/deepos-portmaster-aarch64.tar.gz
export EXTRA_CORES_PACKAGE=/w/build/deepos-extra-cores-aarch64-r2.tar.gz
export STAGE=/w/build/rootfs-stage-candidate
export OUT=/w/build/deepos-rootfs-candidate.squashfs
sh tools/build-rootfs.sh
unsquashfs -cat "$OUT" etc/deepos-version
sha256sum "$OUT"
```

`launcher --selftest` выполняется ARM64-бинарником из `STAGE`. В контейнере без SD и панели ожидается отсутствие локальной библиотеки и framebuffer. На физической V20 результат дополняется фактическими загрузкой, вводом, звуком и записью слота.
