# DEEPoS на R36S‑V20. Сохранения, совместимость и план передачи разработки

Этот документ фиксирует состояние после проверки 0.50 и установки 0.51. Он дополняет [FIRMWARE-SPEC.md](FIRMWARE-SPEC.md), [правила репозитория](../AGENTS.md), [аудит всех 16 настроек](V20-ARCHITECTURE-AUDIT.md) и [метрики](metrics.md). Для следующего агента подготовлены [спецификация настроек и архитектуры](V20-SETTINGS-ARCHITECTURE-SPEC.md) и [стартовый промпт](V20-AGENT-START.md).

## Точка входа для следующего агента

1. Работай из Git-репозитория `deepos`. Сними `git status --short --branch`, `git log -5 --oneline` и `git diff`. Ветка исправлений 0.51 называется `fix/v20-game-exit`. Не сбрасывай чужие изменения. Прочитай `AGENTS.md` и §1, §8, §9, §13, §17 основной спецификации. Сверь версию в Git и на устройстве отдельно.
2. Начни с инвентаря и матрицы P0. Реализуй общий игровой сеанс P1 и сохранения P2, затем пройди P3–P6 по всей матрице. Промежуточный тест открывает следующий этап. Для завершения этапа нужны результаты по всем его строкам. Обновляй журнал и метрики, используй отдельную ветку для следующего блока. Публикация, перезапись SD и перезагрузка физической консоли требуют действующего разрешения пользователя.
3. Перед записью проверь `cat /etc/deepos-version`, `cat /proc/cmdline`, метки разделов в `/sys/class/block/*/uevent` и текущую запись extlinux. В известной конфигурации работали из B, A резервный. Номера устройств сверяй заново. BOOT, ядро, DTB, A, DATA и ROMS не входят в обновление B. Для записи пользовательских разделов нужны резервная копия и подтверждение согласно `AGENTS.md`.
4. Начинай с прямого USB к ПК в текущем состоянии сети. Сначала делай только чтение. VPN бывает выключен и может пропускать локальное подключение. На одном испытании AmneziaVPN блокировал DHCP даже при разрешённом адресе консоли. Если прямой путь действительно заблокирован, можно использовать локальный мост через ВМ `DEEPoS USB recovery` или другой проверенный диагностический канал. Мост не входит в штатную схему. Не меняй состояние VPN без согласования. Отладочный сетевой доступ зависит от `DEBUG.ON` и предназначен для доверенного локального подключения.
5. Воспроизводи симптом через обычное меню. Сохрани версии рантайма, ядра и образа, эффективную конфигурацию и короткий журнал. Разделяй результаты стенда ARM64, теста ввода и физического прогона. Сначала установи, где прервалась цепочка, затем меняй минимальный компонент.

Общий код запуска, ввода, звука и сохранений распространяется на всю прошивку через объявления возможностей рантаймов. Приёмка строится по реестру, фактической поставке и пользовательской библиотеке.

### Как вести и закрывать матрицу

Одна строка на проверяемое сочетание системы, рантайма, ядра и его версии, формата, способа запуска и источника содержимого. Для портов подставлять ID и версию порта. Связывать строку с отдельным именованным тестовым случаем и журналом. Рекомендуемые столбцы для отчёта:

```text
firmware board environment system runtime core build content_id format source bios
start video audio controls sticks volume fn_save exit sram exit_state resume reboot recovery performance evidence
```

Для каждой проверки использовать `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN` или `NOT_APPLICABLE`. `BLOCKED` содержит конкретный BIOS, требуемые данные, рантайм или следующую проверку. `NOT_APPLICABLE` требует подтверждения, что возможность отсутствует по назначению, например у игры без сохранения. Замены ядер и результаты на стенде ARM64 связывать с соответствующей строкой. Статус аппаратной проверки выставлять на V20. Новые или изменённые строки сразу попадают в список повторного прогона. После правки общего слоя повторять автоматическую проверку всей матрицы и аппаратные тесты всех семейств, затронутых изменением. Для полной приёмки у каждой обязательной строки должны быть доказательства по всем применимым полям. Разрешённые исключения публикуются с причиной и точным объёмом поддержки.

### Требования к сохранениям и состояниям

- **Разные типы.** Внутриигровые файлы (`.srm`, `.sav`, EEPROM, карты памяти, конфигурации порта) и снимки памяти эмулятора хранятся отдельно. Обычный запуск использует подходящий внутриигровой сейв. Состояния доступны отдельной операцией с выбором слота. Для новых данных использовать DATA ext4. Сохранить чтение текущих путей ROMS и форматов из K4. Расхождение фактических путей `saved` и §8 основной спецификации закрыть совместимостью при чтении и отдельным документированным решением о миграции.
- **Идентичность.** В метаданных состояния хранить версию схемы, идентификатор системы и содержимого, диск и комплект для многодисковых игр, идентификатор рантайма, идентификатор и сборку ядра, номер слота, длину, контрольную сумму и отметку времени. Учитывать параметры, влияющие на сериализацию. Имя файла отображается пользователю и помогает найти старую копию. Совпадение имени или заголовка недостаточно для автоматического переноса. Ссылаться на алгоритм ROM ID из §8 и хранить его версию. При совпадении быстрого ключа двух образов уточнять идентичность хешем данных. Полное хеширование можно делать по запросу или при первом сохранении с кэшем. Запуск большой игры не зависит от полной хеш-проверки библиотеки.
- **Смена ядра.** При смене сборки или ядра предлагать новый запуск с совместимым внутриигровым сейвом либо прежнее ядро для существующего состояния. Автозагрузка разрешена только с проверенной совместимостью. Версия по умолчанию совпадает с записанной. Держать старые состояния отдельно от новых. Копировать SRAM между ядрами только после подтверждения общего формата или явного выбора пользователя. Не конвертировать по расширению. Бэкап сохраняется и при откате прошивки A/B.
- **Целостность.** Данные и метаданные записывать в новые файлы на одном ext4, завершить запись `fsync`, опубликовать одной операцией обновления ссылки на поколение и синхронизировать каталог. До публикации прежнее поколение читается. Безопасное восстановление разбирает только собственные временные файлы и оставляет последнюю целую версию. Проверять доступное место, контрольную сумму и границы размера. Для конкурирующих операций применять блокировку на игру либо короткую сериализацию без нового демона.
- **Legacy и импорт.** Сначала инвентаризировать фактические каталоги в режиме чтения. Показывать источник, конфликт версий и объём. Копировать в staging, проверять формат и хеш, публиковать после проверки. Если соответствие названия неоднозначно, показать список и сохранить исходные файлы. Не переименовывать и не стирать пользовательские файлы автоматически. Импорт архива допускает только утверждённую структуру обычных файлов, проверяет пути, объём и количество записей; ссылки и выход из staging отклоняются.
- **Резервное копирование.** Включить всё управляемое DEEPoS, отдельно известные каталоги портов и legacy RetroArch. Создавать согласованный снимок в покое или после завершения записи рантаймом. Архив хранит версионированный манифест с хешами. Проверять чтением до ротации. Дать экспорт на другой носитель и импорт с предварительным просмотром. Копия на той же карте нужна для ошибок пользователя. Защита от отказа карты требует копии на другом носителе.
- **Выход и питание.** При поддержке стейтов штатный выход сначала инициирует автосохранение, затем фиксирует его и возвращает в меню. На коротком отключении питания допустима потеря ещё не зафиксированного прогресса. Предыдущий подтверждённый файл должен читаться. При поломке состояния показать причину и позволить обычный запуск. Выход остаётся доступным для игр без стейтов.
- **Интерфейс.** При совместимом снимке штатный повторный запуск и «Продолжить» восстанавливают точку выхода. В меню игры есть «Запустить без состояния» с сохранением внутриигровых файлов. «Состояния» показывает слот, время, ядро и совместимость. Ротация автослотов и архивов из §8 действует на управляемый набор. Сторонние или ручные файлы сохраняются.

### Fn, автоматическое сохранение при выходе и повторный вход

| Действие | Результат |
| --- | --- |
| Короткое нажатие Fn в игре | Запрос быстрого сохранения без выхода. Один запрос на нажатие, временный файл и проверка готовности, предыдущий быстрый снимок читается до подтверждённой публикации. Показать «Сохраняю», затем результат. Предпочтителен игровой виджет, где он проверен. |
| Fn при активной записи или удержании | Повтор не запускает параллельную запись. Отпускание сбрасывает состояние кнопки. Комбинация Fn с другими кнопками получает отдельное правило и не должна незаметно фиксировать прогресс дважды. |
| `Select + Start` | При заявленной поддержке сохранить текущую точку в автослот выхода. Дождаться подтверждённой записи в пределах измеренного таймаута, затем завершить игру. Если нативный рантайм создаёт состояние при выходе, подтвердить его после штатного завершения до публикации записи «Продолжить». Для выхода с ошибкой сохранения показать причину и дать завершить сеанс. |
| Выход через меню эмулятора, порта или завершение работы из DEEPoS | Использовать нативное автосохранение, если оно доступно и подтверждено. При управляемом завершении системы сначала завершить игровой сеанс и запись. Аварийный сбой либо потеря питания оставляют последнее подтверждённое состояние. |
| Обычный запуск той же игры | По умолчанию автоматически загрузить последнее подтверждённое совместимое состояние выхода для проверенного игрового маршрута. Если пользователь выключил «Продолжать после выхода», выполнить обычный старт. Быстрое сохранение Fn отдельно доступно через «Состояния». |
| Ошибка чтения, смена ядра или ревизии, другая версия игры | Показать причину и предложить обычный запуск либо прежний совместимый рантайм. Не перезаписывать прежний снимок или внутриигровой сейв. Отметить повреждённое состояние, чтобы не повторять безуспешную попытку при каждом запуске. |
| Игра поддерживает только собственное сохранение | Fn вызывает сохранение или контрольную точку только при наличии документированного и проверенного действия порта. Возобновление использует нативное сохранение. Если порт не умеет сохранять из обработчика, показать, где сохранение доступно в самой игре. |
| Игра не поддерживает сохранение | Fn показывает, что возможность отсутствует. Обычный и системный выход остаются доступными. |

У быстрого сохранения и автосохранения выхода разные записи. Хранить предыдущую подтверждённую версию каждого и вести ротацию согласно §8. При совпадении Fn и выхода завершить уже начатую запись либо отменить её безопасно. Автослот выхода получает отдельный запрос на текущую точку. Предыдущий снимок остаётся доступен, пока новый не прошёл проверку.

1. На V20 записать реальные коды Fn и проверить `BTN_MODE`, `KEY_FN` и сочетания контроллера. Лаунчер уже распознаёт Fn в общем вводе. Игровой режим 0.51 обрабатывает выход и громкость, поэтому Fn нуждается в отдельной проверенной маршрутизации. В `tests/fixtures/input_evdev.c` проверить один запрос на фронт, отпускание, удержание, отсутствие Fn, выход во время записи. Не менять кнопку Fn в штатном меню и диагностике. Физический ввод игры продолжает идти по штатным дескрипторам.
2. Выбрать один источник команды сохранения для каждого адаптера. Отключать конфликтующий нативный выход только в проверенном сеансе, где он обгоняет запись. Системный хоткей должен работать при сбое адаптера. Сохранение и загрузка подтверждаются готовым снимком, проверкой целостности и фактом восстановления. Фиксированная пауза или один успешный ответ на команду этого не доказывают.
3. Для RetroArch испытать нативную кнопку сохранения и нативное `savestate_auto_save`/`savestate_auto_load` на поставляемой сборке. Проверить реальный путь файла, поведение SRAM и поддержку сериализации каждого ядра. Использовать приватные временные файлы сеанса и публикацию через `saved`. Привязка к слоту, которую показывает UI, проверяется по реальному положению в игре. Документированный UDP-интерфейс допустим к рассмотрению только после проверки локальной изоляции. Не включать сетевой слушатель на USB или LAN ради Fn. [Настройки RetroArch](https://github.com/libretro/RetroArch/blob/master/retroarch.cfg) · [Команды RetroArch](https://docs.libretro.com/development/retroarch/network-control-interface/)
4. Для PPSSPP и других самостоятельных эмуляторов подтвердить их собственные команды и версии формата. Для портов использовать собственные сейвы. Функция сна либо остановка процесса не заменяет стейт после перезагрузки. Отдельно проверить многодисковые игры, переход диска, перезапуск с TF1 и TF2, блокировки сохранений рантаймом, запись при паузе и выход из аварийного состояния.
5. На V20 начать с игры, в которой видны координаты, кадр или счёт. Сохранить Fn, изменить позицию, проверить восстановление быстрого слота. Затем выйти через `Select + Start`, запустить из меню, сверить точку выхода, повторить после перезагрузки. Прогнать отказ записи, нехватку места, таймаут, повреждённый снимок и смену ядра. Повторить для всех заявленных игровых маршрутов матрицы. Отмечать звук, игровые кнопки, оси, громкость и выход отдельными результатами на той же версии рантайма.

### P6. Установка, кабель и выпуск

- [ ] Проверить раздельно прямой USB без VPN, прямой USB с VPN и доступом к локальной сети, прямой USB при диагностированной блокировке DHCP или локального трафика, а затем условный резерв через ВМ. Начинать с проверки USB-дескриптора, адаптера NCM, выдачи адреса, маршрута и доступа к службе. Проверить переподключение, холодную загрузку, истечение аренды и повторный переход между USB-сетью и USB-файлами. USB-файлы передают владение ROMS одному участнику и восстанавливаются после корректного извлечения. Статический адрес и USB ACM рассматривать как отдельные резервные режимы. Способ, которым успешно прошла проверка, фиксировать в отчёте.
- [ ] Для тестового обновления подготовить предыдущий проверенный образ и сверить SHA‑256 обоих файлов. Считать обратно известное число байт до отката/после записи и проверять каждую контрольную сумму. После загрузки сверить версию, `PARTLABEL`, `checks.txt`, рабочую панель, ввод, звук, быстрый выход, повторный запуск. Не подменять эту проверку `--selftest` в контейнере.
- [ ] Перед выпуском проверить K1–K4, тесты и устройство, журнал, метрики и комплект поставки. Опубликовать покрытие всех 175 систем, всех игровых маршрутов и портов с числом строк по статусам. Отдельно опубликовать проверенные игры пользователя, заявленные форматы и функциональные ограничения. Наличие записи в реестре и загрузка ядра учитываются отдельно от приёмки игры на V20.

## Актуализация в конце каждого раунда

1. Сверить обе спецификации с реальными изменениями. Обновить статусы соответствующих шагов, пути, форматы файлов и известные ограничения в этом документе и в [спецификации настроек и архитектуры](V20-SETTINGS-ARCHITECTURE-SPEC.md). Для формального изменения инвариантов или интерфейсов основной спецификации соблюдать `AGENTS.md` и использовать отдельный коммит `docs:`. Требование, план, эксперимент и проверенный результат отмечать раздельно.
2. Обновить матрицу, `docs/journal.md` и `docs/metrics.md`. Указать дату, коммит и сборку, окружение, сценарий, фактический результат, результат до изменения, оставшиеся `BLOCKED`/`NOT_RUN` и как повторить проверку. Отдельно указать, какая версия собрана и какая подтверждена на консоли после перезагрузки. Если запусков на железе в этом раунде не было, предыдущую отметку о физическом образе сохранить с её версией.
3. Если изменился порядок задач, состояние известного дефекта или точка входа, обновить [стартовый промпт](V20-AGENT-START.md) и первый шаг следующего агента. Сначала проверить ссылки и согласованность документов, затем зафиксировать изменения. Раунд завершается после передачи актуального статуса, доказательств, оставшихся задач и готового следующего шага.

## Команды для стенда

Собирать и запускать в отдельном каталоге внутри контейнера. Рабочая копия Windows может содержать AArch64-объекты, а `tests/run-all.sh` ожидает `/w`. Для полного прогона использовался образ `deepos-build:local` с `mkimage`. Базовый `deepos-cross:local` подходит для сборки rootfs, но в нём отсутствовал `mkimage` для одного из BOOT-тестов.

```sh
git status --short --branch
git diff --check
# В deepos-build:local, из изолированной копии в /w
export CFLAGS='-O2 -std=c11 -Wall -Wextra -Werror -Wno-format-truncation -pedantic -D_GNU_SOURCE'
sh tests/run-all.sh
python3 tests/saved_test.py
python3 tests/launch_test.py
python3 tests/board_test.py
```

После изменений версии обновить только ожидаемые строки `tests/golden/hashes.json` через `python3 tests/run.py --update`. Перепроверить staged diff командой `tools/check-secrets.ps1 -Staged`. Изменения сохранений, BOOT или аппаратных дефолтов сопровождаются выводом конкретных тестов и замером по образцу [metrics.md](metrics.md).

Для сборки прошивки монтировать исходники в `/src` только для чтения и локальный `build/` в `/w/build` в контейнере `deepos-cross:local`. Команды ниже используют пакеты, с которыми собрана 0.51. При отсутствии пакета сначала восстановить его по [EMULATORS.md](EMULATORS.md) и сверить состав. Записать контрольные суммы входов и итоговую версию в журнал. Для отдельного кандидата использовать собственные `STAGE` и `OUT`.

```sh
cd /w
tar -C /src --exclude=.git --exclude=build --exclude=tests/out --exclude='*.o' -cf /tmp/deepos-src.tar .
tar -C /w -xf /tmp/deepos-src.tar
export PORTMASTER_PACKAGE=/w/build/deepos-portmaster-aarch64.tar.gz
export EXTRA_CORES_PACKAGE=/w/build/deepos-extra-cores-aarch64-r2.tar.gz
export STAGE=/w/build/rootfs-stage-candidate
export OUT=/w/build/deepos-rootfs-candidate.squashfs
sh tools/build-rootfs.sh
unsquashfs -cat "$OUT" etc/deepos-version
sha256sum "$OUT"
```

`launcher --selftest` выполняется ARM64-бинарником из `STAGE`. В контейнере без SD и панели ожидается отсутствие локальной библиотеки и framebuffer. На физической V20 результат дополняется фактическими загрузкой, вводом, звуком и записью слота.
