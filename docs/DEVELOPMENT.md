# Разработка DEEPoS

Основная плата разработки — R36S‑V20 с RK3326. Перед изменениями откройте
[AGENTS.md](../AGENTS.md) и разделы 1, 13 и 17
[спецификации прошивки](FIRMWARE-SPEC.md).

## Стек

| Слой | Технологии и расположение |
| --- | --- |
| Загрузка и плата | Rockchip RK3326, цепочка загрузчика U‑Boot, Linux 6.12, Device Tree. Конфигурация платы в [board/r36s-v20](../board/r36s-v20). |
| Система | BusyBox init и mdev, статический userspace AArch64, корневой squashfs в двух слотах, DATA на ext4 и ROMS на exFAT. |
| Лаунчер | C11, RGB565 640×480, fbdev, evdev, растровые шрифты Terminus, короткие звуки меню. Код в [apps/launcher](../apps/launcher). |
| Модули и сохранения | C11-супервизор `modd`, UNIX socket, NDJSON JSON‑RPC, POSIX sh-модули. `saved` отвечает за прототип хранилища, `updatr` за A/B. |
| Игры | RetroArch и ядра AArch64, TOML‑реестр команд, BIOS и файлы пользователя на карте, запуск портов через скрипты. |
| Сборка и диагностика | GNU Make, GCC и AArch64 GCC, Python 3, POSIX sh, Docker, PowerShell для записи и проверки карты в Windows, GitHub Actions. |

## Работа вручную

Клонируйте репозиторий, создайте рабочую ветку и используйте Docker. Команды
ниже рассчитаны на Bash, в том числе внутри WSL. Образ
для проверки содержит компилятор, Python, шрифтовый рендер и файловые утилиты.

```sh
git clone https://github.com/morozzz332-ux/DEEPoS.git
cd DEEPoS
git switch -c feat/my-change
docker build -t deepos-build:local -f tests/ci/Dockerfile .
docker run --rm -v "${PWD}:/src:ro" deepos-build:local -c '
  set -e
  cd /w
  tar -C /src --exclude=.git --exclude=build --exclude=.tmp -cf - . | tar -xf -
  for app in modd saved updatr playdemo; do make -B -C "apps/$app"; done
  sh tests/run-all.sh
'
```

Код копируется во временную файловую систему контейнера. Там же остаются
скомпилированные для ПК бинарники. Для самой прошивки используйте отдельный
чистый checkout или worktree, поскольку кросс-сборка создаёт бинарники в `apps/`.

Для быстрого просмотра конкретного экрана из нативной сборки:

```sh
make -C apps/launcher
apps/launcher/launcher --screen settings --out /tmp/settings.ppm
```

## Сборка прошивки и проверка карты

1. Соберите инструментальный образ
   `docker build -t deepos-cross:local -f tools/cross/Dockerfile .`.
2. Из корня рабочего дерева соберите rootfs. Скрипт подтягивает BusyBox,
   собирает приложения для AArch64 и упаковывает конфигурацию платы.

   ```sh
   docker run --rm -v "${PWD}:/w" deepos-cross:local -c 'sh tools/build-rootfs.sh'
   ```

3. Для V20 сохраните ядро, DTB панели и загрузочную цепочку из проверенной
   конфигурации или соберите изменённые компоненты. Команды для загрузчика
   и исходников ядра доступны в `make help`. Для образа с донором Arch‑R
   Clone используйте [build-v20-image.sh](../tools/build-v20-image.sh).
   Скрипт принимает образ донора, DTBO панели, модуль джойстика, rootfs,
   выходной `.img` и размер в МиБ. Готовый комплект RetroArch можно передать
   через `RETROARCH_PACKAGE`. [Импорт эмуляторов](EMULATORS.md)
   Для расширенного каталога ядер передайте в сборку rootfs переменную
   `EXTRA_CORES_PACKAGE` с архивом, созданным
   [package-extra-cores.py](../tools/package-extra-cores.py). Для EmuSCV
   используйте `--emuscv` и архив с SHA‑256, указанным в скрипте.
   PortMaster
   подключается через `PORTMASTER_PACKAGE`. [Сборка PortMaster](PORTMASTER.md)
4. Запустите `tools/preflight.py` и `tools/verify-image.py` для итоговых
   артефактов. Фиксируйте точную версию, размер и SHA‑256 образа и rootfs в
   [RELEASE.md](RELEASE.md). Полные команды и параметры обоих скриптов
   показываются через `--help`.
5. Пишите полный образ на отдельную тестовую карту. Для существующей карты
   с играми используйте процедуру обновления системного слота с резервной
   копией. На консоли проверьте загрузку, видеовывод, кнопки, звук и запуск
   игр по [плану проверки устройства](DEVICE-TEST-PLAN.md).

## Работа с ИИ-агентом

В начале задачи передайте агенту путь к репозиторию, модель и ревизию консоли,
текущую версию, наблюдаемый симптом и проверяемый результат. Укажите, разрешены
ли сборка, запись карты и публикация на GitHub. Задачи удобно ставить по
компоненту, с наблюдаемым условием приёмки:

> На R36S‑V20 по Y открывается описание выбранного модуля. По B пользователь
> возвращается на прежнюю строку. Найди путь от evdev до экрана, сохрани
> горячие клавиши других вкладок и проверь сценарий на хосте. Работай в
> новой ветке. Проверку физической кнопки отметь отдельно.

Для каждого изменения:

1. Прочитайте [AGENTS.md](../AGENTS.md), сохраните локальные правки владельца,
   сверяйте API и настройки платы с кодом и спецификацией.
2. Воспроизведите проблему, внесите минимальное изменение, запустите
   профильные тесты и полный набор перед записью или публикацией.
3. Укажите в [журнале](journal.md) внесённые изменения. Архитектурные решения
   внесите в спецификацию отдельным коммитом. Фактически измеренные
   показатели внесите в [метрики](metrics.md).
4. Перед записью проверьте, что целевой диск действительно microSD, и
   сохраните пользовательские разделы. Не включайте в коммиты копии карт,
   логи с идентификаторами устройств, ROM, BIOS, пароли и токены.
5. При передаче работы перечислите SHA коммитов, пути к артефактам,
   результаты тестов, изменения карты и оставшиеся проверки на консоли.

Для собственного модуля есть [формат пакета и протокол](MODULES.md).
